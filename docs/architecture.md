# Architecture

Manifest V3 extension built with WXT, TypeScript and React. All the logic lives in the service worker; the side panel is only an interface.

## The Organizer

It is the main module and **the only entry point called by the panel**. Interface:

| Method | What it does |
|---|---|
| `propose(windowId, { force? })` | Computes a proposal for the window and saves it in the state. Reuses the saved proposal (with the user's edits) if it is for the same window and its signature matches the current one, unless `force`; if a computation is in progress it returns that one, without starting a second one. |
| `edit(edit)` | Applies a user edit to the current proposal and saves it in the state. |
| `saveToList(groupId)` | "Save to list": adds a "new AI" group to the category list. |
| `apply()` | Saves the undo snapshot, creates the groups of the current proposal in Chrome, then clears the proposal. |
| `undo()` | Undoes the last applied organization and clears the proposal. |
| `abort()` | "Stop": cancels the requests of the computation in progress; the computation ends without a proposal. |
| `acceptPreview()` | "Use this": like `abort()`, but the computation showing the by-site preview ends with that preview as the current proposal. |
| `rememberSite(tabId)` | "Always put here": saves the site of the tab in the category of its group (list, or open group with the same name). The site is the one of the rule that decides the tab today, moved from its category, or the bare domain. The proposal stays current. |
| `autoGroupTab(tabId)` | Automatic grouping of a tab whose URL just changed, with the site rules only (see "Automatic grouping"). Does not change the state. |
| `state()` | Returns the current state. |

### Automatic grouping (`auto-group.ts`)

The only thing autoGroup does without a click. The service worker listens to `tabs.onUpdated` and, when `changeInfo.url` is present, calls `organizer.autoGroupTab(tabId)`, which goes through the `exclusive` queue like the other operations. Only URL changes count, not reloads: a tab the user takes out of a group by hand stays out until it opens another page.

- Off with `settings.autoGroupSites === false` (*Settings > Categories and sites*; on by default). It applies in both modes and never queries an AI.
- The tab must be free (`isFreeWebTab`: not pinned, not in a group, a web page, not of an excluded domain). The title does not count, because at the moment the URL changes the page is usually still loading.
- The category comes from `createSiteMatcher`, so the most specific site wins, as in the proposal.
- If the tab's window has an open group named like the category (case-insensitive) the tab joins it, even alone, without changing its name and color.
- Otherwise the free tabs of the window with the same category (in strip order) form a new group with the category's name and color, only if they reach `minTabs`.
- No undo snapshot. Errors (e.g. a window that does not accept groups) are logged and the tab stays where it is.
- The state does not change: a proposal containing the tab becomes stale and the panel shows "Your tabs changed". `autoGroupSites` is left out of the signature, so toggling it does not make a proposal stale.

### Proposal edits

The panel does not edit the proposal by itself: it sends a `ProposalEdit` and receives the updated state. The possible edits:

| `kind` | Effect |
|---|---|
| `rename` (`groupId`, `name`) | Renames the group (leading and trailing spaces removed). |
| `recolor` (`groupId`, `color`) | Changes color, among Chrome's 9. |
| `remove-tab` (`tabId`) | Removes the tab from the proposal: it will stay ungrouped. |
| `move-tab` (`tabId`, `toGroupId`) | Moves the tab to the end of another group of the proposal. |
| `discard-group` (`groupId`) | Discards the group: its tabs stay ungrouped. |

A group left without tabs disappears from the proposal. Edits to nonexistent groups or tabs are ignored. Since the edited proposal is saved in `storage.session`, the edits survive closing the panel, and "Apply" always uses the edited version.

### Save to list (`save-to-list.ts`)

Only for groups with provenance `ai`. The new category takes the group's **current name and color** in the proposal (so also those changed by the user) and a description requested from the Generator with `describe` (the same Generator as the pipeline). The Generator receives the name and up to 8 example tabs, with title and cleaned URL.

- Generator missing or in error: the category is saved with an empty description and the notice invites the user to complete it in the settings (with a link to the Categories section).
- A category with the same name already exists (case-insensitive): no duplicate, notice.
- After saving, the group becomes `list` and the proposal's signature is updated with the new list: the proposal stays current (the categories changed, but the proposal already takes them into account), so reopening the panel does not lose the edits. The tabs are read only once, before requesting the description: if the proposal was already stale it stays stale, and a tab opened during the description (up to 30 s) makes it stale.
- The outcome goes in the state's `notice` field (i18n key and name), shown in the panel; the next edit removes it.

### Queued operations

All operations (`propose`, `edit`, `saveToList`, `apply`, `undo`) go through the `exclusive` queue and are executed one at a time, in order of arrival. Each one reads the state, possibly touches the tabs and rewrites the state: without the queue, a proposal computed during "Apply" could overwrite the old undo snapshot. `state()` is a single read and does not go through the queue. Neither does `abort()`, because it must act precisely while the computation occupies the queue.

A `propose` that arrives while another one is in progress or queued shares its result only if it is for the same window and without `force`. For another window, or with "Recompute", a new computation is queued: otherwise the second window's panel would receive the first window's proposal.

### Stop

Each `propose` creates an `AbortController` at request time, before entering the queue, and passes its signal to `buildProposal` → `runPipeline` → adapters → `fetch` (or Prompt API). `abort()` aborts it: the requests in progress fail immediately, even while waiting before a retry, and the computation ends in `phase: 'idle'`, with no proposal, with the `popupAborted` notice. The undo snapshot stays. In the panel the "Stop" button appears next to "Computing the proposal…". `abort()` stops all computations in progress and queued: a computation stopped while still in the queue ends the same way without making any request.

### By-site preview and "Use this"

With local providers the AI proposal arrives in 10–30 s, and after a timeout the user would get the grouping by domain anyway, which costs a few milliseconds. For this reason, in AI mode, `propose` immediately computes the by-site proposal (`buildPreview`, that is `domainGroups` (site rules, then domain) on the same tabs) and puts it in the `computing` state as `preview`. The panel shows it read-only while the AI works: no renaming, colors, moves or "Apply".

- The preview exists only if the AI will actually be queried (`willAskAi`): AI mode, at least one candidate tab and a usable Classifier or Generator (or Gemini Nano available). In by-site mode, or without providers, the proposal is already immediate.
- When the AI proposal arrives, the `ready` state replaces it and `preview` disappears.
- **"Use this"** (`acceptPreview()`): stops the computations like "Stop", but with the reason `accept-preview`. The computation that had a preview ends in `ready` with that preview as the proposal: editable, applicable, with no notices. It has the same signature as the AI proposal that was about to arrive, so reopening the panel reuses it without new calls; "Recompute" asks the AI again. A computation still in the queue, with no preview, ends as with "Stop".
- **"Stop" does not change**: as the PRD requires, it produces no proposal, not even the by-site one.

### Computation times (`stopwatch.ts`)

Each `propose` that actually computes measures its phases with a stopwatch: `inputs` (`collectInputs`), `preview` (preview and first save of the state), `descriptions`, `classifier`, `generator`, `domain` (fallback or by-site mode) and `total`. A phase that does not start does not appear. The times, in whole milliseconds, go to the service worker log (`autoGroup: tempi del calcolo (ms)`) and to `proposal.timings`, so the smoke test and the measurement scripts read them from `storage.session`. They are diagnostics only: they are not part of the signature and the panel does not show them.

### Proposal signature

Each proposal has a `signature`: IDs and URLs of the candidate tabs, open groups (ID, name, color), settings used, availability of the providers and of Gemini Nano, and whether description reading is on. When the panel reopens, `propose` rereads the inputs and compares the signature: if it matches it returns the saved proposal (with the user's edits), otherwise it computes a new one. The title is not part of the signature, because it often changes by itself (counters like "(3) Mail").

### AI pipeline (`pipeline.ts`)

Implements the whole fallback table of the PRD:

| Classifier | Generator | Behavior |
|---|---|---|
| yes | yes | step 1 (Classifier), then step 2 (Generator "new only") on the remaining tabs |
| yes | no | step 1 only: the remaining tabs stay ungrouped |
| no | yes | Generator in "full" mode |
| no | no | grouping by domain |

**Always a proposal**: except with "Stop", every provider error is recorded as a notice (`recordFailure`) and the pipeline drops one level; an unexpected error, which is not a `ProviderError`, is recorded as "invalid response" instead of interrupting the computation. Only an aborted signal is rethrown.

If a provider fails, the pipeline drops one level: Classifier in error → row 3 (or 4 without Generator); Generator in error in full mode → row 4; Generator in error at step 2 → the remaining tabs stay ungrouped (row 2). Each drop adds a notice with level, provider and cause (`recordFailure`).

**Choice of the Classifier** (`resolveClassifier`): the configured one (preset other than "None" and base URL; the model is optional, because Kev and Rizzo Flow serve only one) if it has the host permission; without permission, none and a `no-permission` notice.

**Step 1** (`classifyThenGenerate`): the Classifier returns a choice and a confidence for each tab. The tabs that become "remaining" are those with confidence below the threshold (default 0.7), with the choice "none of the above" or unreadable, and those of a category that would be left with fewer tabs than the minimum (same `applyGroupRules`). A single tab can join an existing group.

If there are no options (no category and no open group) the Classifier is not queried, because it could only answer "none": the pipeline moves to row 3 or 4.

**Step 2**: only if there is a Generator **and** the remaining tabs are at least `minTabs` (otherwise no new group would be valid, so no call). The Generator receives only the remaining tabs, in "new only" mode, with the known options so that it does not duplicate them. The groups of step 1 and step 2 are merged by name (`mergeByName`) and go through `applyGroupRules` only once: new groups below the minimum are dissolved and the colors are assigned in a single place.

**Site rules** (`site-rules.ts`): before any level, the candidate tabs whose URL matches a site of a category (`settings.categorySites`, category ID → `domain[/path]`) are taken out. A domain matches its subdomains, a path matches by whole segments, case-insensitively; with several matches the most specific site wins (host labels + path segments, then the longer path). The other tabs follow the normal path: only they are read by the Description reader and sent to the Classifier or Generator. Rule groups are `ValidGroup`s with the same short IDs and are merged by name with the groups of the AI or of the domain grouping before `applyGroupRules`, so they follow the same minimum: a rule tab below the minimum stays ungrouped and is never passed to step 2. If every candidate is taken by a rule, no AI is queried and there is no preview. Tabs placed by a rule carry `rule` (the site) in the proposal; moving them clears it.

**Mode** (`settings.mode`): with `domain` (*By site*) `runPipeline` immediately returns the groups by domain, without notices, without reading pages or querying providers. With `ai` (default) it follows the fallback table.

**Choice of the Generator** (`resolveGenerator`): it is the user's choice, with no substitutions.

- **OpenAI-compatible server** (preset or custom): used if it has URL, model and host permission. Without permission the `no-permission` notice is added and the pipeline drops one level: Gemini Nano does **not** take its place, because the user chose another model.
- **Gemini Nano** (`preset: 'nano'`, the default): used if `LanguageModel.availability()` returns `available`; with `downloadable` or `downloading` it is not used and the `needs-download` or `downloading` notice is added; with `unavailable` (or without Prompt API) no notice.
- **None** (`preset: 'none'`): no Generator; Nano is not even queried.

Nano's availability is read in `collectInputs` only in AI mode with Nano chosen, and it is part of the signature: when the download finishes, the next proposal is recomputed.

**Page descriptions** (`description-reader.ts`): if the option is on and the `<all_urls>` permission is granted (`inputs.readDescriptions`), and only if there is at least one AI level to query, before the calls the pipeline reads the meta description (or `og:description`, if the former is missing or empty) of the candidate tabs with `chrome.scripting.executeScript`, all in parallel and with a maximum time of 500 ms per tab. Tabs put to sleep by Memory Saver (`discarded`) are never read, because reading them would wake them up; non-`http(s)` pages, the Web Store and PDFs are also skipped. A tab that does not answer in time or is not accessible keeps title and URL. Tabs of excluded domains never get here, because the selection has already discarded them. The description (at most 300 characters, whitespace collapsed) becomes `AiTab.description`, so it reaches both the Generator and the Classifier (in the `state`). With grouping by domain nothing is read.

**Description cache**: the descriptions read stay in `storage.session` (`descriptionCache`, by URL, at most 1000 entries), including "page without description". A new computation reads only the new pages. A page that did not answer in time or was not accessible is not remembered, so it is retried the next time. A sleeping tab with an already-read URL gets its description back without being woken up.

**Classifier cache** (`classification-cache.ts`, `withClassificationCache`): the pipeline's Classifier is wrapped in a per-tab cache in `storage.session` (`classifierCache`, at most 1000 entries). Only tabs never seen with the same options are sent to the server. The key is the SHA-256 hash of base URL, model, options (names and descriptions), title, cleaned URL and description of the tab: changing a category, the model or the page reclassifies. The threshold stays out, so changing it costs no requests. Unreadable responses (confidence 0) are not remembered. The Classifier is deterministic, so the cache also applies with "Recompute". If a request fails nothing from that computation is remembered. Measurement with local Rizzo Flow and 30 tabs: 14.3 s with an empty cache, 0.48 s after opening a tab, 3 ms for "Recompute" or for a threshold change.

**Gemini Nano session ahead of time**: before reading the pages the pipeline calls `generator.prepare?.(mode, language)` ("new only" mode if there is a Classifier, otherwise "full"). Gemini Nano thus creates the session while the pages are being read and the Classifier works. The OpenAI-compatible Generator has no `prepare`.

**Full mode**, step by step:

1. `prepareTabs`: for each candidate tab a short ID (`t1`, `t2`, …), the title and the cleaned URL (`cleanUrl`: host and path, without scheme, credentials, query or fragment). The `byShortId` table maps the short IDs back to Chrome tabs, which never leave the extension. Tabs of excluded domains are not there, because they were discarded by the selection.
2. `buildOptions`: categories of the list, then open groups with a name. An open group with the same name as a category (case-insensitive) takes the category's place and uses its description; the others have the description "Group created by the user: “name”" (from `chrome.i18n`).
3. `generator.generate({ mode: 'full', tabs, options, language })`, with `language` from the i18n key `aiLanguageName` ("italiano", "English").
4. `validateGroups`: discards non-string names, empty names, new names longer than 2 words (the names of known options are accepted even if longer), nonexistent IDs, and tabs assigned to more than one group (they stay ungrouped); merges groups with the same name.
5. `applyGroupRules`: a name that matches an option becomes that option (provenance `existing` or `list`), otherwise an `ai` group. Existing groups accept even a single tab and keep name and color; categories and new groups require at least `minTabs` tabs (the excluded tabs end up in `leftover`, which will be used by step 2 of AG-08). Colors: categories use their fixed color, which is reserved, then new groups rotate among the colors still free in the window.

If the Generator throws a `ProviderError`, the pipeline adds a notice `{ level: 'generator', provider, cause }` and falls back to grouping by domain. Errors of other kinds (bugs) are not hidden.

### System One adapter (`src/ai/systemone-classifier.ts`)

TypeSafe contract (verified on Jev's public documentation): `POST {URL base}/v1/systemone` with `{ model?, state, questions }`, where `questions` is an **object** that maps the question name to the definition `{ type: 'choice', instructions, criteria }`; the response has `answers`, an object with the same question name and `{ type, choice, probabilities, confidence }`.

- `criteria`: name → description of each option (categories and open groups), at most 254, plus `none_of_the_above` as TypeSafe recommends, for a total of at most 255. A `none_of_the_above`, unknown or unreadable choice leaves the tab without a category (so "remaining"), without making the others fail.
- `state`: the tab as an object `{ title, url, description? }`, with the same cleaned URL sent to the Generator.
- `model` only if filled in (Jev: `jev-latest`); `Bearer` key only if present.
- 5 s timeout per request; retry and causes as for the Generator (see "Error handling").
- **Request strategy**: `per-tab` (default) sends one request per tab with at most 4 requests in parallel; at the first error no further request starts and those in progress are aborted, because the pipeline drops one level anyway; `batch` sends a single request with `state` = all the tabs and one question per tab (question name = short ID). See "Classifier strategy" below.
- `testSystemOneConnection`: a minimal question.

### Error handling (`src/ai/http.ts`)

The HTTP transport is shared by the two adapters, so the behavior is uniform:

| Situation | Retry | Notice cause |
|---|---|---|
| 429, 529 | one, after 0.8 s | `rate-limit` ("too many requests") |
| 5xx | one, after 0.8 s | `unreachable` ("not reachable") |
| 401, 403 | no | `invalid-key` ("invalid API key") |
| 400, 404, 422 | no | `invalid-request` ("rejected the request") |
| network error | no | `unreachable` |
| timed out (Classifier 5 s, Generator 30 s, per request) | no | `timeout` |
| unreadable or off-schema response | no | `invalid-response` |

- The times are in `TIMINGS` (`classifier`, `generator`, `retryDelay`), a single place to change; the tests shorten them in `tests/setup.ts`.
- The timeout uses `deadline()`, an explicit `setTimeout` combined with the "Stop" signal. `AbortSignal.timeout` is **not** used: combined with `AbortSignal.any` it is held only by weak references, and a hanging request with no other references can let the garbage collector collect the timer, so the timeout never fires (it happened in the tests: a test stuck for 1051 s).
- Gemini Nano does not use HTTP but applies the same maximum time as the Generator with `deadline()`.
- The notices show provider and base URL, e.g. "OpenRouter (https://openrouter.ai/api/v1) is not reachable.", and appear at the top of the preview with a link to the right section of the settings (Classifier or Generator).

### Classifier strategy

The AC of AG-08 asks to choose by measuring. During development no System One server was available (neither a Jev key, nor Kev or Rizzo Flow installed), so:

- both strategies are implemented and tested (`strategy: 'per-tab' | 'batch'`);
- the default is **`per-tab` with 4 requests in parallel**, for quality reasons: the `state` contains a single tab, so the classifier cannot confuse the tabs with each other, while in `batch` each question sees all the tabs and must find the right one through the ID in the instructions. The cost is similar: in `per-tab` the `criteria` are repeated in every request, in `batch` they are repeated for every question (TypeSafe states $0.042 per million input tokens). The stated latency is 70–500 ms per request: with 30 tabs and 4 requests in parallel that is about 8 rounds, 1–4 s;
- `scripts/measure-classifier.mjs` measures the two strategies on a real server (median time, input tokens, agreement between the strategies, correct choices on 10 example tabs).

**Measurements (AG-13, 2026-10-04).** Local Rizzo Flow (`rizzo-flow-1.7b-q8_0`, llama.cpp on Apple M4, Metal), 30 tabs, 3 runs per strategy:

| Strategy | Total time (median) | Input tokens | Expected choices |
|---|---|---|---|
| `per-tab`, 1 request at a time | 11.6 s (1 run) | 10,344 | 30/30 |
| `per-tab`, 4 in parallel | 11.7 s | 10,344 | 30/30 |
| `batch` | 10.1 s | 7,684 | 29/30 |

The two strategies give the same choice for 29 tabs out of 30.

**Decision: `per-tab` with 4 requests in parallel stays.**
- `batch` is only 14% faster and costs 26% fewer tokens, but it is a single request of about 10 s: it exceeds the Classifier's maximum time of 5 s per request, so in the extension it would always time out.
- With `per-tab` each request takes about 0.4 s, each one stays well under 5 s even when queued, and the accuracy is full.
- Rizzo Flow executes requests one at a time, so parallelism does not speed it up. It does not slow it down either, and it helps with servers that work in parallel, such as Jev.
- With 30 tabs the local Classifier therefore takes about 12 s. With Jev the stated latency is 70–500 ms per request, so with 4 in parallel 1–4 s; not measured, because a TypeSafe key is missing.

### OpenAI-compatible adapter (`src/ai/openai-generator.ts`)

- `POST {URL base}/chat/completions` with `model`, `temperature: 0`, two messages (instructions; JSON with options and tabs) and `response_format: { type: 'json_schema', json_schema: { name: 'tab_groups', strict: true, schema } }`. The schema asks for `{ "groups": [{ "name": string, "tabs": [string] }] }`.
- `max_tokens: 4096` (`GENERATE_MAX_TOKENS`), reasoning included. The useful response is small; the cap matters with reasoning models, because after a timeout a local server can keep generating for minutes (measured: over 13 with 30 tabs) and keep the GPU busy for the next computation. A response cut by the cap is not complete JSON and becomes "invalid response".
- If the server answers 400 (typically because it does not support structured output, or because the model rejects `max_tokens`, like OpenAI's reasoning models) it retries once with the minimal request, without `response_format` or `max_tokens`, relying on the instructions and on validation. The response can also be in a ```json block.
- In "new only" mode the options arrive by name only (`["Lavoro", "Notizie"]`): they serve only to avoid repeating their names, and the descriptions would be extra tokens to process. In "full" mode they arrive with the description.
- Reasoning is not configurable: without reasoning, in the test with Unsloth Studio, the model answered with one group per tab, which the validator would discard, and the parameters to turn it off change from server to server (`chat_template_kwargs`, `reasoning`, `think`).
- API key as `Authorization: Bearer …`, only if present (optional for local servers).
- Timeout, retry and error classification: see "Error handling".
- `describe`: a request without schema (`temperature: 0.2`, `max_tokens: 1000`, which includes any reasoning) that asks for one sentence in the browser's language; a truncated response (`finish_reason: "length"`) is not saved; otherwise it is cleaned of quotes and spaces and cut to 300 characters (`cleanDescription`).
- `testOpenAiConnection`: a minimal request (`max_tokens: 1`) that checks URL, key and model.

Adding a compatible provider means adding an entry to `GENERATOR_PRESETS`: the pipeline does not change.

### Gemini Nano adapter (`src/ai/nano-generator.ts`)

Same contract (`Generator.generate` and `describe`) and same instructions and schema as the OpenAI adapter, but through Chrome's Prompt API (`LanguageModel`): no key, no data leaves the computer.

- Base session with `initialPrompts: [{ role: 'system', … }]`; every prompt uses `responseConstraint: GROUPS_SCHEMA` to constrain the response.
- **Reused base session**: it is created once per system prompt (that is, per mode and language) and kept in memory as long as the service worker stays alive, at most 4. It never receives a prompt: it is only measured and cloned, so it stays clean. `prepare` starts it ahead of time; the following computations find it ready. A failed or timed-out creation, or a session that stops working (e.g. destroyed by Chrome), leaves the cache and the next computation creates a new one. The cache is tied to the `LanguageModel` object, which the tests replace.
- **Chunking**: the budget is the base session's free context (`contextWindow − contextUsage`, with fallback to `inputQuota`/`inputUsage` for earlier versions of Chrome) minus 25% left for the response. If the prompt with all the tabs exceeds the budget, the tabs are distributed into chunks measured with `measureContextUsage`, with all the measurements in parallel; each chunk has at least one tab and a small margin for the names that will arrive.
- Each chunk runs in a clone of the base session, so the context does not accumulate. The names invented in the previous chunks are added to the options of the following chunks (with an empty description); groups with the same name across chunks are then merged by the validator.
- Errors: session creation failed → `unavailable`; any other Prompt API error (clone, measurement, prompt, e.g. context exceeded) → `invalid-request`; off-schema response → `invalid-response`. The pipeline falls back to domain with the notice.
- Maximum time: 30 s for each call (session creation, measurement, each chunk), as for each HTTP request of the OpenAI-compatible Generator; with many tabs the total computation can therefore last longer without timing out.
- **Language**: Chrome asks to declare the input and output language on every `availability()` and `create()` (`expectedInputs`, `expectedOutputs`), otherwise it warns in the console. Nano answers only in de, en, es, fr and ja: `nanoLanguage()` uses the browser's language if it is one of these, otherwise English, and in that case the prompt asks for the names in English (`withNanoLanguage`), consistent with the declared language.
- `nanoAvailability()` and `downloadNano(onProgress)` are used by the options page.

### `propose` flow

```
collectInputs(windowId)                          buildProposal(inputs)
  tabs.query ─► selectCandidateTabs ─┐             runPipeline
  tabGroups.query ───────────────────┤               ├─ Generator (full) ─► validation ─► rules and colors
  loadSettings ──────────────────────┼─► inputs ─►   └─ (none / error) ─► domain + notice
  API key (local), host permission ──┘                                   │
                                                          Proposal ─► chrome.storage.session
```

0. **Settings**: `loadSettings()` reads from `storage.sync` the minimum number of tabs and the excluded domains, on every proposal (so a change applies from the next proposal).
1. **Tab selection**: keeps only the window's tabs that are not pinned, not already in a group, with an `http`, `https` or `file` URL (so no `chrome://`, new tab, extension pages), with a real title (not empty and different from the URL, as happens during loading) and not belonging to an excluded domain or one of its subdomains. The exclusion happens here, at the first step, so excluded tabs never reach the following steps (and in the future the AI).
2. **Grouping by domain**: hostname without `www.`; a domain becomes a group only with at least `minTabs` tabs (default 2). If there is already an open group named like the domain (case-insensitive), that site's tabs go there, even a single one, with provenance `existing`: as for the AI, a single tab can join an existing group. Groups follow the order of the first tab of each domain. `domainGroups` builds `ValidGroup`s by domain and passes them through `applyGroupRules` with provenance `domain`.
3. **Colors**: the assigner counts the colors of the groups already open in the window and gives each new group the first least-used color, in Chrome's order (grey, blue, red, yellow, green, pink, purple, cyan, orange). This way the free colors are used up first, then the rotation starts again. The `reserve()` method will be used for the categories' fixed colors (AG-05/AG-06).

`buildProposal` delegates to `runPipeline`. The API key is read in `collectInputs` but never enters the signature or the state.

### `apply` flow

The applier rereads the window's tabs and skips those closed, moved or grouped in the meantime. Before touching any tab it takes the snapshot of the tabs involved (see below) and saves it in the state: if the service worker stops halfway, "Undo" remains possible. For each new group it calls `tabs.group` and then `tabGroups.update` with name and color; for existing groups (since AG-06) it adds the tabs with `tabs.group({ groupId })` without touching name and color. The IDs of the created groups end up in the snapshot (`createdGroupIds`).

### Undo

The snapshot (`UndoSnapshot`) contains, for each tab involved, window, position and original group (or none). `undo()`:

1. ignores tabs that are no longer open;
2. removes from the groups the tabs that the operation grouped (`tabs.ungroup`);
3. puts each tab back in its original position with `tabs.move`, from left to right, so each index refers to the already rebuilt strip (indices beyond the end are clamped to the last position);
4. puts back into their original groups the tabs that had one, if the group still exists (needed from AG-06, when tabs can join existing groups);
5. if a moved tab ended up in the middle of someone else's group (in that case Chrome adds it to the group) it removes it.

The created groups disappear by themselves when they are left without tabs. Tabs opened afterwards are not touched, groups are never renamed. After the undo the proposal is cleared, because it was computed with the tabs still grouped.

The snapshot stays available until another organization is applied (computing a new proposal does not delete it) or until Chrome closes (`storage.session`). The panel shows "Undo last organization" only in the window the snapshot refers to.

## State and persistence

The state lives in `chrome.storage.session` under the `organizer` key:

```ts
interface OrganizerState {
  phase: 'idle' | 'computing' | 'ready';
  windowId?: number;
  proposal?: Proposal;   // groups + warnings (+ timings, diagnostics only)
  preview?: Proposal;    // only in "computing" with AI: read-only by-site proposal
  undo?: UndoSnapshot;   // present while "Undo" is available
  notice?: { key, arg }; // outcome of the last operation, e.g. "Save to list"
  error?: string;        // i18n key of the last error
}
```

The state always has the `windowId` it refers to: it is unique for all windows, and the panel shows only the updates of its own window. Opening the panel in another window replaces the previous proposal.

It survives closing the panel and restarting the service worker, but not closing Chrome. If the panel closes during the computation, the service worker finishes anyway and saves the proposal; when the panel reopens, `propose` finds the proposal ready and returns it.

Storage split required by the PRD: `sync` for categories and preferences, `local` for API keys, `session` for the Organizer's state. `session` also holds the pipeline's two caches, `classifierCache` and `descriptionCache` (`session-cache.ts`, at most 1000 entries each, the oldest are evicted): like the state, they disappear when Chrome closes, so titles and URLs do not stay on disk.

### Categories

interface Category { id: string; name: string; description: string; color: GroupColor }

## Side panel

`entrypoints/sidepanel`: WXT declares it as `side_panel.default_path` and adds the `sidePanel` permission. The service worker calls `sidePanel.setPanelBehavior({ openPanelOnActionClick: true })`, so clicking the icon (and `_execute_action`, that is `Alt+Shift+G`) opens the panel instead of a popup. **Why:** a popup closes at the first click outside, while with local providers the computation can last tens of seconds; the panel stays open while the user switches tabs and while the AI works.

On opening it reads the current window and requests `organizer/propose` with the saved mode.

**Mode choice in the panel.** Below the top bar there is a segmented button *By site* / *With AI*: changing it saves `settings.mode` and recomputes immediately, so the user chooses the type of classification before applying. Below the selector there is a summary of what will be used: the active providers (e.g. "Rizzo Flow → Unsloth Studio" or "Gemini Nano") with the link to change them, or "No AI provider set up". The settings are read live (`storage.onChanged`), so the panel also updates if the user changes them in the options page.

**The whole window, not just the proposal** (`src/organizer/window-view.ts`, `buildWindowView`). The panel reads its own window's tabs and groups live and overlays the proposal on them. The function is pure and tested, and splits the window into four sections:
- **New groups**: the proposal's groups that do not exist yet, editable as before.
- **Open groups**, in strip order: Chrome name and color (locked), the tabs they have now (view only) and those that the proposal adds, marked "new" and removable or movable. A group with no additions stays collapsed.
- **Ungrouped**: the ungrouped (free) tabs that the proposal leaves out, with "Add to…".
- **Not organized** (collapsed): pinned tabs, browser pages, excluded domains and loading tabs, with the reason.

**Close the tab.** Each row has ✕ "Close tab" (also tabs of open groups, ungrouped and not organized ones); "−" removes the tab from the proposed group leaving it open. The panel calls `organizer/close-tab`, and `Organizer.closeTab` closes the tab and removes it from the proposal, in the operation queue. If the proposal was current and the tab was not in an open group, the signature is recomputed after closing, so reopening the panel reuses the proposal without new AI calls. If instead the tab was the last one of an open group that the proposal extends, the group disappears: the signature stays old and the proposal stale, so as not to apply tabs to a group that no longer exists. Closes done from the panel do not make the stale-proposal notice appear.

**`add-tab` edit.** "Move to…" and "Add to…" use the new edit `{ kind: 'add-tab', tab, to }`, where `to` is a group of the proposal or an open group that the proposal does not touch yet. In this second case the proposal receives a new `existing` group (`id: e<idChrome>`). The Organizer (`checkAddTab`) accepts only a tab already in the proposal or still ungrouped in the window, with the same rules as the selection, and only towards a group of that window. The tab's data is reread from the browser, not taken from the message.

Material 3 structure:
- top bar with the title and ⚙ for the settings;
- during the computation, indeterminate linear progress bar and "Stop"; with AI, below, the read-only by-site preview (dimmed cards) and "Use this";
- scrolling content;
- action bar fixed at the bottom: "Undo last organization", "Recompute" (outlined button), "Apply" (filled button).

The outcomes ("Groups created.", "Save to list") appear in a *snackbar*. Without a proposal there is an empty state with the message of the last operation.

Each group is an outlined card:
- color dot, which opens the palette of the 9 colors;
- editable name: confirmed with Enter or by leaving the field, Esc cancels; existing groups are locked and have the lock icon;
- provenance label, colored for "list" and "new AI";
- number of tabs;
- "Save to list" for "new AI" groups;
- ✕ to discard the group.

Each tab has favicon and title, with the URL in the tooltip. On hover "Move to…" (icon with the transparent native menu on top) and ✕ appear.

**Stale proposal** (`useTabChanges`): the panel stays open, so it listens to the tab and group events of its own window. What counts: tabs created, closed, moved between windows and changes of URL, pinning or group; title and favicon do not count, as they change by themselves. If they arrive while there is a proposal, it shows "Your tabs changed after this proposal." with "Recompute". It does not recompute by itself: each computation can cost AI calls. Events caused by "Apply" and "Undo" do not count.

The style follows Material Design 3 in CSS, without `@material/web`, which is in maintenance only and has no Expressive version on the web:
- **colors:** `--md-sys-color-*` roles generated with `@material/material-color-utilities` (Tonal Spot scheme from Chrome blue `#1a73e8`) in `src/ui/md3-tokens.css`, for light and dark theme. They are regenerated with `npm run theme`;
- **typography, shapes and motion:** `--md-sys-typescale-*`, `--md-sys-shape-corner-*` tokens and the motion curves in `src/ui/base.css`;
- **icons:** Material Symbols Rounded imported as SVG (`?raw`), so no remote font and no requests to Google;
- **exception:** the only hand-written colors are Chrome's 9 group colors, which are data and not theme.

The panel contains no grouping logic.

## Permissions

Required: `tabs`, `tabGroups`, `storage`, `scripting`, `sidePanel` (added by WXT for the side panel, with no warnings at install). Optional: `optional_host_permissions: ["http://*/*", "https://*/*", "<all_urls>"]`, from which only the host of the configured provider (on save) and `<all_urls>` (when descriptions are turned on) are requested. Only the smoke test build (`AUTOGROUP_SMOKE=1`) grants `<all_urls>` in advance, because in headless mode permission requests cannot be accepted.

Check in the normal build (`scripts/permissions-check.mjs`): with no host permissions at startup, the click on the Generator's "Save" and the one on the descriptions switch open Chrome's dialog; a request made outside a gesture is rejected ("This function must be called during a user gesture").

**Provider host inside `<all_urls>`** (`removeDescriptionPermission`): if a provider's host is granted while `<all_urls>` is already active, Chrome may answer yes without registering it separately, and turning descriptions off would also remove access to the provider. In headless mode it is not possible to verify what Chrome does, so the code covers both cases: turning descriptions off removes `<all_urls>`, checks the hosts of the configured providers and immediately requests those left without permission, still within the click on the switch (transient user activation). If Chrome had registered them nothing is requested. If the user refuses, an invitation to save the provider again appears below the switch.
